# 通用数据权限设计与实现说明

## 背景

底座的数据权限不能写死为公司、组织或某个行业对象。不同项目可能按租户、项目、范围、课程、负责人、创建人或自定义业务字段隔离数据。

## 结论

`sweet-auth-base` 已按“通用数据权限模型”落地，不再把公司、部门、HRDB 这类业务实体写进底座。

第二版的核心是：

1. 权限维度可配置，例如租户、项目、课程、业务范围、负责人、创建人。
2. 菜单或低代码表声明自己受哪个维度控制，以及维度落在哪个字段上。
3. 角色或用户只保存结构化的数据范围，不保存 SQL。
4. 低代码列表、详情、新增、编辑、删除都走统一的数据权限解析；固定系统页列表也支持同一套列表过滤。
5. 控制器不自己拼 `tenant_id`、`owner_id` 之类的条件。

这套模型能做 SaaS、企业中台、在线学习、CRM 或其他业务系统。区别只在配置的数据权限维度和绑定字段不同，底座代码不需要知道具体业务是什么。

## 当前状态

当前系统已经实现的是菜单权限、按钮权限、接口权限，以及通用数据权限基础模型：

- 维度由 `sys_data_dimension` 定义，不写死具体业务实体。
- 菜单通过 `sys_data_scope_binding` 绑定维度、表编码、字段编码和生效动作。
- 角色通过 `sys_role_data_scope` 保存常规范围策略。
- 用户通过 `sys_user_data_scope_override` 保存临时覆盖或收窄/扩展。
- 低代码列表、详情、创建、更新、删除会复用解析后的结构化范围做行级检查。
- 固定系统页只要菜单绑定了数据表，也可以配置数据权限；列表查询会应用同一套结构化范围。
- 角色权限保存时可以同时保存菜单、按钮和角色数据权限，避免权限保存到一半的中间态。

当前树形范围先按指定值保存，后续可以在维度来源表稳定后扩展“包含下级”的展开策略。底座仍不应内置公司、部门或其他具体业务实体。

不要在文件控制器或某个业务控制器里再临时写一套数据归属判断来替代通用数据权限。后续新增导出、批量操作、文件预览和下载的业务记录上下文时，也应复用同一套规则。

文件访问权限当前只负责判断文件本身是否存在、是否允许预览或下载；业务记录归属，例如某条订单、某篇文章、某个客户是否属于当前用户，应交给未来的数据权限层统一处理。

## 第一版和第二版的差别

第一版容易做成固定业务字段权限：

```text
用户 -> 租户列表 -> 查询时拼 tenant_id IN (...)
```

这种做法适合单个业务系统，但不适合底座。因为在线学习平台可能按 `tenant_id`、`course_id` 或 `school_id` 控制，CRM 可能按 `owner_id` 或 `region_id` 控制，通用项目管理也可能按 `scope_id` 或 `project_id` 控制。

第二版改成配置化维度：

```text
用户/角色 -> 数据权限范围 -> 菜单/表绑定维度 -> 字段 -> 统一查询条件
```

例如：

| 项目场景 | 维度 | 菜单或表字段 | 范围值 |
| --- | --- | --- | --- |
| 示例中心 | 业务范围 | `scope_id` | 1、2 |
| 示例中心 | 项目 | `project_id` | 1001、1002 |
| 在线学习 | 学校 | `school_id` | 2001 |
| 在线学习 | 课程 | `course_id` | 3001、3002 |
| CRM | 负责人 | `owner_id` | 当前用户 ID |
| 多租户 SaaS | 租户 | `tenant_id` | 当前租户 ID |

这样底座只理解“维度、字段、范围值”，不理解具体业务。

## 目标

- 数据权限维度可配置，不绑定某个业务实体。
- 低代码表、普通菜单、按钮接口可以复用同一套数据范围规则。
- 控制器不拼权限条件，统一由 service/repository 前的权限解析层生成查询范围。
- 前端只做配置和展示，不允许前端提交原始 SQL。
- 数据权限修改需要审计，便于排查“为什么看不到数据”。

## 核心模型

### 1. 权限维度

建议新增“数据权限维度”配置，用来描述某类数据边界。

示例字段：

- `code`：维度编码，例如 `tenant`、`project`、`demo_scope`、`owner`。
- `name`：维度名称。
- `value_type`：值类型，例如 `number`、`string`、`tree`。
- `source_type`：取值来源，例如字典、低代码表、组织树、固定枚举。
- `source_code`：来源编码，例如表编码或字典编码。
- `label_field` / `value_field`：展示字段和取值字段。
- `parent_field`：树形维度的父级字段。
- `state`：是否启用。

示例：

```json
{
  "code": "demo_scope",
  "name": "业务范围",
  "value_type": "number",
  "source_type": "table",
  "source_code": "demo_scope",
  "label_field": "scope_name",
  "value_field": "id",
  "state": true
}
```

### 2. 菜单或表绑定

一个菜单或一张低代码表需要声明它支持哪些数据权限维度，以及该维度落在哪个业务字段上。

示例：

- 用户管理绑定 `department`，字段是 `dept_id`。
- 订单管理绑定 `tenant`，字段是 `tenant_id`。
- 示例事项绑定 `demo_scope`，字段是 `scope_id`。

建议字段：

- `menu_id` 或 `table_code`
- `dimension_code`
- `field_code`
- `match_type`：等于、包含、树包含、本人等。
- `required`：是否必须配置。

示例：

```json
{
  "menu_id": 1201,
  "table_code": "demo_ticket",
  "dimension_code": "demo_scope",
  "field_code": "scope_id",
  "match_type": "in",
  "required": true
}
```

如果一张表需要多维度控制，例如事项既要限制业务范围，又要限制项目，可以绑定多条规则。运行时默认取交集：

```text
scope_id IN (...) AND project_id IN (...)
```

### 3. 角色授权

角色授权时选择某个菜单的数据范围。

建议支持：

- 全部数据
- 本人数据
- 本部门/本组织
- 本部门及下级
- 指定范围
- 无数据

指定范围保存为结构化值，例如 JSON 数组，而不是 SQL。

建议第二版以“角色授权”为主，“用户授权”为补充：

- 角色数据权限：常规权限来源。
- 用户数据权限：只用于临时覆盖或特殊人员。
- 多角色合并：建议同一维度取并集，不同维度取交集。

例子：

```json
{
  "role_id": 8,
  "menu_id": 1201,
  "dimension_code": "demo_scope",
  "strategy": "specified",
  "values": [1001, 1002]
}
```

如果策略是本人数据，不需要手工填值：

```json
{
  "role_id": 9,
  "menu_id": 1301,
  "dimension_code": "owner",
  "strategy": "self",
  "values": []
}
```

### 4. 运行时解析

请求进入 service 后，根据当前用户、菜单、表编码和接口动作解析数据范围。

建议输出统一结构，例如：

```go
type DataScope struct {
	FieldCode string
	Operator  string
	Values    []any
}
```

repository 层只接收结构化条件并转成 GORM 查询，避免控制器里拼查询条件。

建议运行时流程：

1. 中间件只负责登录和基础接口权限。
2. 控制器解析当前访问的是哪个菜单、表和动作。
3. service 调用数据权限解析器，得到结构化范围。
4. repository 的查询构建器统一追加数据权限条件。
5. 详情、编辑、删除先按 ID 查询时也必须追加同一套条件，避免只拦列表不拦详情。

示意：

```text
HTTP 请求
  -> 登录校验
  -> 菜单/按钮/接口权限
  -> 解析数据权限
  -> repository 追加查询条件
  -> 返回数据
```

不要在 `FileController`、`GeneralizationController`、业务控制器里各写一套数据权限判断。文件预览和下载如果要判断业务归属，应通过“文件引用的业务记录”回到统一数据权限层判断，而不是在文件控制器里按 `table_code` 临时拼条件。

## 建议表结构

第二版可以考虑新增或调整下面几类表。命名可以后续按项目风格再定。

### 数据权限维度表

保存“有哪些可授权维度”。

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `code` | 维度编码 |
| `name` | 维度名称 |
| `value_type` | 值类型 |
| `source_type` | 数据来源 |
| `source_code` | 字典编码、表编码或系统来源 |
| `label_field` | 展示字段 |
| `value_field` | 值字段 |
| `parent_field` | 树形父级字段 |
| `state` | 是否启用 |

### 菜单数据权限绑定表

保存“某个菜单或低代码表按哪个字段受控”。

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `menu_id` | 菜单 ID |
| `table_code` | 表编码 |
| `dimension_code` | 维度编码 |
| `field_code` | 当前表里的受控字段 |
| `match_type` | 匹配方式 |
| `required` | 是否必须配置范围 |
| `state` | 是否启用 |

### 角色数据权限授权表

保存“角色在某个菜单上的数据范围”。

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `role_id` | 角色 ID |
| `menu_id` | 菜单 ID |
| `dimension_code` | 维度编码 |
| `strategy` | 全部、本人、指定范围、无数据等 |
| `scope_values` | JSON 数组，保存指定范围 |
| `state` | 是否启用 |

### 用户数据权限覆盖表

不是第一阶段必须，但可以预留。用于给某个用户临时扩大或缩小范围。

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `user_id` | 用户 ID |
| `menu_id` | 菜单 ID |
| `dimension_code` | 维度编码 |
| `strategy` | 覆盖策略 |
| `scope_values` | JSON 数组 |
| `expire_at` | 过期时间，可选 |
| `state` | 是否启用 |

## 配置示例

### 通用 Demo：事项只看指定业务范围

1. 建维度 `demo_scope`，来源表 `demo_scope`。
2. 事项菜单绑定 `demo_scope` 维度，字段为 `scope_id`。
3. 角色“范围 A 用户”授权 `demo_scope` 范围为 `[1]`。
4. 查询事项时自动追加：

```text
demo_ticket.scope_id IN (1)
```

### 在线学习：老师只看自己课程

1. 建维度 `course`，来源表 `edu_course`。
2. 课程内容菜单绑定 `course` 维度，字段为 `course_id`。
3. 老师角色授权策略为“指定范围”，范围来自老师被分配的课程。
4. 课程内容列表、详情、编辑和文件预览都只允许访问授权课程下的数据。

### 多租户：所有业务表按租户隔离

1. 建维度 `tenant`。
2. 所有租户隔离表绑定 `tenant_id`。
3. 登录后从用户上下文得到当前租户范围。
4. repository 统一追加 `tenant_id` 条件。

这种场景可以做成全局维度，避免每个菜单重复配置。

## 前端配置入口

建议放在角色权限分配里增加“数据权限”区域：

- 左侧仍选菜单。
- 右侧按钮权限之外增加“数据权限”页签。
- 每个菜单展示已绑定的维度。
- 管理员选择范围策略和具体范围值。

低代码表结构管理里可以增加“数据权限字段”配置，但只负责声明字段，不负责给角色授权。

建议页面：

1. 数据权限维度管理：维护维度、来源表、展示字段、值字段。
2. 表结构管理：配置当前表的数据权限字段。
3. 菜单管理或发布弹框：绑定菜单和表的数据权限维度。
4. 角色管理：给角色分配菜单权限、按钮权限、接口权限和数据权限。
5. 用户管理：可选，做用户级临时覆盖。

权限排查时建议展示：

- 当前用户有哪些角色。
- 当前菜单绑定了哪些数据权限维度。
- 每个维度最终解析出的范围值。
- 最终追加到查询上的字段和操作符。

这样管理员能知道“为什么看不到数据”。

## 与已有固定字段权限的迁移

如果当前已有固定字段数据权限，可以按下面过渡：

1. 初始化一个对应的数据权限维度。
2. 将已有使用固定字段隔离的菜单绑定到 `tenant_id`、`project_id` 或现有业务字段。
3. 将原来的角色范围迁移成“指定范围”。
4. 保留兼容查询一段时间，等新模型稳定后再移除旧逻辑。

## 需要继续讨论

- 是否允许用户级覆盖角色数据权限。
- 多角色数据权限是取并集还是交集，通常建议取并集。
- 详情接口是否也强制走数据权限，建议必须走。
- 导出、批量操作、统计接口是否复用同一套数据权限，建议必须复用。
- 树形范围是否需要缓存，以及缓存刷新时机。

## 第一阶段落地建议

如果要在 `sweet-auth-base` 里开始实现，不建议一次做满所有复杂场景。可以按下面顺序推进：

1. 建维度表和菜单绑定表。
2. 低代码表结构管理增加“数据权限字段”配置。
3. 角色权限分配增加“数据权限”页签。
4. 低代码列表、详情、编辑、删除统一接入解析结果。
5. 文件预览和下载暂时只管文件本身；等业务记录数据权限稳定后，再通过文件引用回到业务记录判断。
6. 增加权限排查面板，展示当前用户对当前菜单的最终数据范围。

第一阶段不要做的事：

- 不要把数据权限写死为公司、部门或 HRDB。
- 不要允许前端提交原始 SQL。
- 不要在每个控制器里各写一套字段判断。
- 不要只限制列表，不限制详情、编辑、删除和导出。
