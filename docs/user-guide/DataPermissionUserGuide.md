# Sweet Platform 数据权限管理员操作手册

## 适用对象

本手册面向 Sweet Platform 的系统管理员、实施人员和权限管理员，用于完成数据权限配置、检查和效果验证。

本手册不介绍数据库、代码或技术实现。开发边界见[平台工程架构与目录手册](../engineering/PlatformEngineeringGuide.md)，具体接入步骤见[平台扩展开发指南](../engineering/ExtensionDevelopmentGuide.md)。

## 1. 数据权限是什么

功能权限和数据权限解决两个不同问题：

| 权限类型 | 回答的问题 | 示例 |
| --- | --- | --- |
| 功能权限 | 用户能否进入菜单、打开页面或调用某项功能 | 是否可以进入“运输订单”页面、是否可以执行导出 |
| 数据权限 | 用户进入功能后，可以查看、修改、删除或导出哪些数据 | 只能查看本组织及下级组织的运输订单 |

只有功能权限而没有相应数据授权时，用户可能可以进入页面，但看不到受保护的数据。反过来，数据授权也不会替代菜单和按钮权限。

Data Permission 是 Sweet Platform 的平台底座能力，为不同业务模块提供统一的数据范围配置方式。它不是 TMS、WMS 或 SRM 自己的业务权限，也不会代替这些系统的业务状态、流程审批或操作规则。

## 2. 整体配置流程

数据权限应按以下顺序配置：

```mermaid
flowchart LR
    A["数据资源<br/>确定保护什么数据"] --> B["归属定义<br/>确定数据归谁"]
    B --> C["权限策略<br/>定义允许什么范围"]
    C --> D["权限授权<br/>授予角色或用户"]
    D --> E["配置检查<br/>确认配置完整有效"]
    E --> F["启用并验证<br/>业务查询生效"]
```

推荐操作步骤：

1. 在“系统管理 > 数据权限”中创建数据资源，并配置资源支持的操作。
2. 为资源配置至少一项归属定义。
3. 创建可复用的权限策略，并为策略配置规则。
4. 将角色或用户、数据资源、资源操作和权限策略关联起来。
5. 分别检查资源、策略和授权，处理全部错误。
6. 启用配置，使用不同范围的测试账号验证列表、数量和详情。

不要跳过配置检查直接启用资源。资源、归属、策略或授权之间有任一处不匹配，平台都会拒绝启用或安全地返回无数据。

## 3. 数据资源配置

### 3.1 什么时候需要创建数据资源

当某类业务数据需要按组织、法人、人员或其他业务维度限制可见范围时，应创建数据资源。

例如，“运输订单”是一类需要保护的业务对象，可以创建资源编码为 `transport_order` 的数据资源。资源代表运输订单这类数据，不代表运输订单菜单，也不代表页面地址或接口地址。

### 3.2 主要配置项

| 配置项 | 说明 | 建议 |
| --- | --- | --- |
| 资源编码 | 资源的稳定标识，创建后不应变化 | 使用简短、清晰、可长期复用的英文编码，如 `transport_order` |
| 资源名称 | 管理员能够理解的业务名称 | 使用“运输订单”等业务对象名称 |
| 资源类型 | 说明资源由低代码表、固定业务服务或报表承载 | 按实施方案选择，不要根据菜单形式选择 |
| 权限状态 | 表示该资源是否启用数据权限 | 完成归属、策略、授权和检查后再启用 |
| 状态 | 表示资源配置本身是否可用 | 停用前先确认对现有授权的影响 |

资源创建时数据权限默认关闭。创建资源不会自动生成归属、策略或授权，也不会自动让任何用户获得数据。

### 3.3 资源操作

同一资源的查询、详情、修改、删除和导出是不同操作，应按实际业务需要分别配置和授权。例如，物流经理可以拥有运输订单的查询和详情范围，但不一定拥有删除或导出范围。

## 4. 归属定义配置

### 4.1 为什么数据需要归属

平台只有知道“一条数据属于谁”，才能把用户可访问的范围和业务数据对应起来。

归属定义描述数据所属的业务维度。例如：

| 业务数据 | 归属编码示例 | 业务维度 | 含义 |
| --- | --- | --- | --- |
| 运输订单 | `owner_org` | 管理组织 | 订单属于哪个经营管理单元 |
| 业务单据 | `legal_entity` | 法人主体 | 单据由哪个法律或核算主体承担 |
| 客户资料 | `owner_employee` | 企业人员 | 客户由哪位人员负责 |

一个资源可以有多项归属。例如运输订单可以同时具有管理组织、法人主体和负责人归属。配置策略时必须明确选择其中一项，平台不会自动选择“第一项”，也没有默认主归属。

### 4.2 两种绑定方式

**metadata_field**

适用于平台低代码数据。实施人员从平台已经登记并校验通过的字段中选择归属，不需要输入数据表、字段表达式或查询语句。

**registered_field**

适用于 TMS、WMS、SRM 等固定业务模块。业务模块需先由服务端注册可用于数据权限的归属能力，管理员只能选择已经注册且与当前资源匹配的项目，不能临时输入自由字段。

两种方式都只负责说明“归属值在哪里以及代表什么维度”，不负责决定当前用户可以访问哪些组织或人员。

### 4.3 配置注意事项

- 归属编码在同一资源内必须唯一，创建后不要改变。
- 业务维度必须与归属含义一致，例如管理组织归属不能绑定为企业人员维度。
- 绑定方式和绑定目标属于身份配置，启用并被策略使用后不能随意修改。
- 停用或删除前，应先确认没有有效策略规则正在使用该归属。

## 5. 权限策略配置

权限策略用于描述一套可以重复授权的数据范围规则。例如：

- 本组织。
- 本组织及下级组织。
- 本人负责的数据。
- 指定业务范围。

策略本身不直接属于某个数据资源。只要目标资源具有与策略规则相匹配的归属，策略就可以复用。

### 5.1 策略规则

每条规则需要明确：

| 配置项 | 业务含义 |
| --- | --- |
| 归属 | 使用资源中的哪一种数据归属 |
| 维度 | 归属值代表管理组织、法人主体还是企业人员 |
| 范围来源 | 当前用户的有效组织、当前员工或指定范围 |
| 关系 | 只包含当前对象，还是包含当前对象及下级 |
| 匹配方式 | 使用单值匹配或集合匹配 |

“本组织及下级组织”策略可以配置为：

- 归属：管理组织归属。
- 维度：管理组织。
- 范围来源：当前员工的有效管理组织。
- 关系：`self_and_descendants`，即当前组织及下级组织。
- 匹配方式：集合匹配。

如果一个策略包含多条规则，平台要求这些规则同时满足。例如，策略同时要求“属于本组织”并且“属于当前有效法人”，数据必须同时符合两个条件。

## 6. 权限授权配置

权限授权用于建立以下关系：

```text
角色或用户
    ↓
数据资源及操作
    ↓
权限策略
```

V1 支持向角色和用户授权。

### 6.1 推荐做法

- 优先向角色授权，让相同职责的账号共享同一套规则。
- 用户直接授权只用于临时、例外或无法通过角色表达的场景。
- 不要为每个用户创建一套内容相同的策略。
- 不要通过角色名称猜测数据范围，角色只有在明确配置授权后才产生数据权限。
- 查询、详情、修改、删除和导出应分别按最小需要授权。

例如，可将“物流经理”角色在“运输订单”的查询和详情操作上，授权使用“本组织及下级组织”策略。拥有该角色的用户会根据自己的有效组织得到不同结果，而不是共享一组手工填写的固定组织。

## 7. 配置检查

配置检查用于在启用前确认资源、归属、策略和授权能够完整衔接。管理员可以分别检查数据资源、权限策略和权限授权。

常见失败及处理方式：

| 失败情况 | 常见原因 | 处理建议 |
| --- | --- | --- |
| Ownership 不存在 | 策略使用的归属编码在目标资源中没有对应定义，或归属已停用 | 为资源补充正确归属，或调整策略使用的归属 |
| Policy 规则不匹配 | 归属编码一致但业务维度不同 | 统一归属和规则的维度，不要只看名称相近 |
| Dimension 错误 | 范围来源或关系不支持当前业务维度 | 选择该维度支持的范围来源和关系 |
| Grant 配置错误 | 角色、用户、资源、操作或策略已停用或不完整 | 恢复有效状态或重新选择有效对象 |
| 资源启用失败 | 没有有效归属，或已有策略、授权未通过检查 | 逐项完成资源、策略和授权检查后再次启用 |

配置检查通过只代表配置关系完整。正式启用后仍应使用有代表性的账号验证实际数据结果。

## 8. 验证权限效果

### 8.1 推荐验收方法

至少准备三类账号：

1. 能访问某一组织范围的账号。
2. 能访问另一组织范围的账号。
3. 有功能入口但没有对应数据授权的账号。

分别验证：

- 列表只出现范围内的数据。
- 分页总数与列表范围一致。
- 有权数据可以打开详情。
- 无权数据不能通过已知编号直接打开详情。
- 如已配置修改、删除或导出，还应分别验证对应操作。

### 8.2 平台 Demo 场景

平台验收场景以运输订单为例：

| 测试账号 | 组织范围 | 应看到的订单 | total |
| --- | --- | --- | --- |
| 用户 A | 华东物流中心及其下级 | ORD001、ORD002 | 2 |
| 用户 B | 华南物流中心 | ORD003 | 1 |
| 无授权用户 | 无 | 无数据 | 0 |

详情结果必须与列表一致：用户 A 不能查看 ORD003，用户 B 不能查看 ORD001 和 ORD002，无授权用户不能查看任一订单。无权查看时，平台不会向用户透露该订单是否真实存在。

### 8.3 TMS 车辆按公司过滤的正确做法

当前开发数据中虽然已有 `tms_company`、`tms_vehicle` 和 `tms_waybill`，车辆和运单也都有 `company_id`，
但这些公司 ID 与 Organization 中的法人主体或管理组织 ID 不是同一套身份。当前还没有一张可信映射说明：

```text
TMS company_id
    对应哪个法人主体？
    对应哪个管理组织？
```

因此，平台现在不能根据登录账号安全地猜出默认 TMS 公司。只在前端把公司条件自动选中并不能形成数据权限，
用户仍可能通过直接调用详情 API 或改请求参数访问其他公司数据。

正式接通时应按以下顺序实施：

1. 确认 TMS 公司代表法人范围还是管理范围，不能同时含糊使用两种含义。
2. 建立稳定映射，让每个 `tms_company` 关联一个受信任的 Organization 法人主体或管理组织。
3. 将 TMS 用户显式绑定到 `SysUser -> Employee`，并为 Employee 维护有效法人和任职范围。
4. 为 `tms_vehicle`、`tms_waybill` 分别创建数据资源，不能复用当前 Demo 的 `transport_order` 资源。
5. 用 `company_id` 建立各资源的 Ownership，并把它连接到第 2 步的映射关系。
6. 创建“当前公司”“当前公司及下级”等策略，再给角色或用户授予查询、详情等操作。
7. 用华东、华南和无授权三个账号验证列表、total 和已知 ID 详情。

**只有一个可访问公司时**：后端仍负责强制过滤；页面可以把该公司作为只读的当前范围提示，并在高级查询中显示初始化条件，
让用户知道自己正在看哪家公司。这个显示条件不能代替后端数据权限。

**有多个可访问公司时**：默认查询应表示“全部有权公司”，后端用允许集合过滤；用户可在高级查询中进一步选择一家或几家公司。
不要把当前所有公司 ID 自动写进查询方案，因为员工任职和授权变化后，已保存的 ID 集合会过期。查询方案只能缩小数据权限结果，不能扩大结果。

当前可立即验证的是平台 Demo `transport_order`；TMS 车辆/运单必须先完成上述映射和资源接入，不能把 Demo 通过当作 TMS 已受保护。

### 8.4 一步步验证当前 Demo

1. 在“组织管理 > 人员与任职”确认测试 Employee 已绑定测试 User，并存在有效管理任职。
2. 在“系统管理 > 数据权限 > 数据资源”确认 `transport_order` 已启用，查询和详情操作可用。
3. 在“归属定义”确认 `owner_org` 指向 Demo 表的管理组织字段，维度为管理组织。
4. 在“权限策略”确认规则使用 `owner_org`、当前员工有效管理组织和“本组织及下级组织”。
5. 在“权限授权”把策略授予测试角色的查询和详情操作，不要只授予菜单权限。
6. 分别用华东范围、华南范围和无数据授权账号重新登录。
7. 在运输订单列表记录每个账号的行数和 total，再把另一范围的订单 ID 直接放入详情地址验证拒绝访问。
8. 修改 Grant 或任职后重新发起请求；不需要等待全局权限缓存，但必须确认配置已启用并通过检查。

## 9. 常见问题

### 9.1 为什么用户看不到数据？

请依次检查：

1. 用户是否具有页面和接口的功能权限。
2. 用户账号、有效角色和企业人员绑定是否正常。
3. 目标资源及对应操作是否启用数据权限。
4. 角色或用户是否具有该资源操作的有效授权。
5. 策略规则与资源归属是否精确匹配。
6. 用户当前是否具有有效组织、法人或人员事实范围。
7. 配置检查是否全部通过。

无授权或配置异常不会自动放开全部数据。

### 9.2 为什么配置检查失败？

先查看检查结果中的对象和错误说明，再确认归属编码、业务维度、范围来源和状态是否一致。不要通过复制新策略来绕过原有错误，否则容易形成多套含义相同但互相冲突的配置。

### 9.3 为什么资源启用失败？

资源启用前必须至少有一项有效归属，所有使用该资源的策略规则和授权也必须有效。先分别执行资源、策略和授权检查，再处理检查结果。

### 9.4 为什么修改后权限没有立即生效？

平台按请求解析数据权限，不依赖长期保存的全局权限结果。修改后请确认配置已经保存并处于启用状态，然后刷新业务页面发起新请求。若仍未生效，应检查账号当前角色、人员绑定、资源操作和配置检查结果，而不是等待缓存自动刷新。

### 9.5 为什么不能直接输入组织范围？

管理组织、法人和员工范围来自平台可信的组织主数据。管理员通过策略选择“本人”“本组织”或“本组织及下级”等范围语义，平台再依据当前用户的有效组织关系计算结果。直接输入组织范围容易形成过期或伪造数据，因此不作为常规授权方式。

### 9.6 为什么列表、数量和详情必须一起验证？

三者必须使用相同的数据权限结果。只验证列表可能遗漏分页总数泄露或通过已知编号访问详情的问题。发现三者结果不一致时，应停止上线并交由平台维护人员排查。

## 10. 管理规范建议

### 10.1 资源编码

- 使用稳定、清晰的英文小写编码，单词之间使用下划线，例如 `transport_order`。
- 编码表达业务对象，不使用菜单名称、页面地址或接口地址。
- 资源投入使用后不要修改编码。

### 10.2 归属命名

- 名称应直接表达归属含义，例如 `owner_org`、`legal_entity`、`owner_employee`。
- 同一含义在不同资源中尽量使用一致命名。
- 不使用“字段一”“默认归属”等缺少业务语义的名称。

### 10.3 策略复用

- 按稳定的业务规则建立策略，例如“本组织及下级组织”。
- 不要每个用户创建一个 Policy。
- 不要复制大量内容相同、名称不同的 Policy。
- 变更公共策略前，应确认所有使用该策略的授权对象和资源。

### 10.4 授权原则

- 优先角色授权，用户授权作为例外。
- 只授权业务需要的资源操作。
- 临时用户授权应记录原因并定期复核。
- 停用账号、角色、资源或策略后，应重新执行配置检查。

### 10.5 变更与验收

- 重要变更应先在测试环境配置。
- 使用不同组织范围和无授权账号完成对照验证。
- 验证列表、total、详情以及已授权的写操作。
- 检查通过并完成业务验收后再在正式环境启用。

## 11. 当前能力边界

当前 V1 已支持：

- 低代码数据通过 `metadata_field` 配置归属并进入统一查询权限链路。
- 固定业务模块使用的 `registered_field` 公共注册和执行框架。
- 管理组织的当前组织和本组织及下级组织范围。
- 法人主体和企业人员的当前精确范围。
- 列表、分页总数、详情、修改、删除、批量删除和导出的统一权限处理。

当前尚未完成或存在以下限制：

- `registered_field` 尚未接入真实 TMS、WMS、SRM 业务数据，具体业务模块接入后仍需独立验收。
- 新增数据时的通用归属赋值和新归属校验能力尚未完整形成；业务接入时必须明确新增规则。
- 法人主体和企业人员当前只支持精确范围，不支持下级关系；管理组织支持本组织及下级组织。
- 当前没有独立的数据权限诊断页面，管理员主要通过配置检查和业务账号验收定位问题。
- 当前账号需要至少一个有效角色才能建立数据权限上下文；仅配置用户直接授权但账号没有任何有效角色的场景不在 V1 支持范围内。
- 固定业务模块接入、复杂报表数据集和更多业务维度需要分别设计与验收，不能仅凭已有框架认定已自动支持。
