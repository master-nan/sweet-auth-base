## 2. 任务目标与边界

本任务建立 Sweet Platform Logger & Audit 最小兼容基线：

1. 为平台 HTTP 请求统一生成或透传 `request_id`、`trace_id`。
2. 统一访问日志中的 actor、resource、action、result、error 审计语义。
3. 让失败响应、技术错误和访问记录通过同一组关联 ID 定位。
4. 保留现有访问日志、登录日志、Report 执行日志和查询 API。
5. 固定技术日志、访问日志和业务审计的职责边界。

本任务不是日志平台重构，不引入 ELK、APM、分布式 Tracing、新日志表或第二套审计框架，也不批量修改业务 Controller。

## 4. 日志体系审计结果

### 4.1 当前日志类型

| 类型 | 当前实现 | 结论 |
| --- | --- | --- |
| 技术日志 | 全局 Zap logger，记录运行异常、数据库或系统错误及中间件诊断信息 | 继续作为运行诊断，不承担业务审计 |
| 访问日志 | 全局 `LogHandler` 对业务路由写入 `access_log`，保存请求、响应、状态和耗时 | 作为 HTTP 请求权威记录 |
| 操作审计 | `access_log` 已有用户、菜单、action 和 resource 字段，部分操作由路径分类 | 继续在同一记录上形成审计投影，不新增审计表 |
| 登录日志 | `login_log` 保存登录用户名、IP 和属地 | 保留现状，不与访问日志合并 |
| 领域执行日志 | Report 等模块拥有领域执行日志 | 保留领域业务语义，不并入通用访问日志 |

### 4.2 已满足能力

1. `LogHandler` 已全局覆盖经过平台业务中间件的 HTTP 路由。
2. 请求体、查询参数和响应已有 64 KiB 边界。
3. 密码、Token、验证码、签名 URL 等敏感内容已有脱敏。
4. 访问日志已有 `user_id/user_name`、`menu_id`、`action` 和 resource 字段。
5. T005 的统一错误响应使中间件能读取安全客户端错误。
6. 现有 `/admin/log/access/query` 和 `/admin/log/access/:id` 提供列表与详情查询。

### 4.3 本任务发现并处理

| 问题 | 风险 | 本任务处理 |
| --- | --- | --- |
| 无统一 request/trace ID | 技术错误、客户端请求和访问日志不能稳定关联 | 增加统一上下文、响应头和持久化字段 |
| 错误只能从响应正文间接判断 | 审计结果和错误码不明确 | 标准化 `result/error_code/error_message` |
| 合法 JSON 若没有 `success` 字段会被误判失败 | 非标准成功响应记录错误 | 使用可空 `success`，缺失时回退 HTTP 状态和 Gin errors |
| Controller 无法显式提供审计语义 | 只能持续扩展硬编码路径分类 | 增加可合并的 `SetAuditContext` |
| 技术日志重复打印完整请求和响应 | 日志噪音及敏感信息暴露面较大 | 成功请求只记录结构化摘要，正文仅留在脱敏访问日志 |
| 错误和 panic 技术日志无关联 ID | 难以跨日志定位 | `ResponseHandler` 和 `CustomRecovery` 增加关联字段 |

## 5. 统一边界

### 5.1 技术日志

技术日志使用 Zap，服务于程序运行诊断：

- 必须携带可获得的 `request_id` 和 `trace_id`。
- 可以记录 method、path、错误类别和内部错误链。
- 不在 Info 日志重复打印完整 request/response。
- 不替代持久化访问日志或领域执行日志。

### 5.2 访问日志

`access_log` 每个 HTTP 请求一条记录，负责：

- 请求关联：`request_id`、`trace_id`。
- Actor：现有 `user_id`、`user_name`。
- 请求信息：method、URL、IP、status、duration。
- 受控载荷：脱敏、截断后的 body、query、response。
- 审计投影：menu、action、resource、result、error。

### 5.3 业务审计

通用操作审计继续投影在 `access_log`：

- actor：`user_id`、`user_name`；
- resource：`resource_type`、`resource_code`、`resource_id`；
- action：`action`；
- result：`result`、`success`、`status_code`；
- error：`error_code`、安全的 `error_message`。

领域模块仍可保留 Report execution log 等专用业务日志，但不得复制 HTTP 请求日志能力。

## 6. 本次修改

### 6.1 请求与审计上下文

新增 `backend/middleware/log_context.go`：

1. 接受合法的 `X-Request-ID` 和 `X-Trace-ID`。
2. 缺少 request ID 时生成 UUID。
3. 缺少 trace ID 时继承 request ID。
4. 拒绝超长或包含不安全字符的外部关联 ID。
5. 将两个 ID 写入 Gin context 和响应 Header。
6. 提供 `RequestID`、`TraceID` 和 `SetAuditContext`。
7. 多次设置 AuditContext 时只用非空字段增量覆盖。

### 6.2 AccessLog 字段

在现有模型上增加：

- `request_id`
- `trace_id`
- `result`
- `error_code`
- `error_message`

没有新增日志表，也没有修改现有日志查询接口路径或请求 DTO。现有 AutoMigrate 注册会为部署环境补充模型列；本任务未新建手工 migration 或 SQL。

### 6.3 中间件

`LogHandler`：

1. 请求进入时初始化关联上下文。
2. 保留原有路径分类规则。
3. 显式 AuditContext 优先覆盖自动分类的非空字段。
4. 在认证中间件执行后读取用户上下文。
5. 从最终统一响应提取安全错误码和错误消息。
6. 访问日志写入失败时记录关联 ID。
7. 每个请求只输出一条结构化完成摘要，不再输出完整请求和响应正文。

`ResponseHandler`：

1. 统一错误日志增加 request/trace ID。
2. 删除无业务信息的 start/end Info 日志。
3. 不改变成功或错误响应结构。

`CustomRecovery`：

1. panic 技术日志增加 request/trace ID。
2. 不改变既有恢复和客户端响应行为。

## 10. 遗留问题

以下历史问题按任务边界只记录：

1. 登录日志当前在异步 goroutine 中使用 Gin context，并且只记录登录尝试的基础字段，尚无结果和错误语义；需要独立任务审计生命周期及成功/失败模型。
2. `AccessLogRetentionDays` 已有配置，但当前未发现统一清理任务；日志保留与归档需后续独立设计。
3. AccessLog 列表 Repository 使用明确列集合，本任务为保持查询接口不变未把 request/trace/error 字段加入列表筛选；当前可从详情和数据库定位。
4. 自动 action/resource 分类只覆盖部分历史路径；应由新增模块通过 `SetAuditContext` 增量接入，不应在本任务批量改 Controller。
5. 访问日志仍同步写数据库，沿用现有行为；高流量下的异步化和降级策略不属于本任务。
6. panic 由外层 recovery 记录关联技术日志；现有中间件顺序下不会生成完整的 panic 访问日志，后续如需补齐必须单独评审 recovery 与响应落库顺序。
7. 当前只建立关联 ID，不是分布式 Trace，不提供 span、采样、链路拓扑或 APM。
8. 登录日志和访问日志缺少统一保留策略执行器，不能在本任务顺手引入 Job 或日志平台。

## 11. 后续模块必须遵守

1. 新增 Organization/Integration 接口必须沿用全局 LogHandler。
2. 需要明确业务操作时调用 `SetAuditContext`，不得自行直接写 AccessLog。
3. Service 和技术日志应从上下文读取 request/trace ID，不生成第二组关联 ID。
4. Integration 技术执行日志属于领域运行记录，不替代平台访问日志。
5. 敏感载荷不得通过普通 Zap Info 日志输出。
6. 业务错误继续通过 T005 标准错误链返回，避免依赖字符串判断。
