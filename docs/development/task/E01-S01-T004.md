## 2. Task 目标

本任务建立 Sweet Platform Service 层最小事务边界基线，明确：

```text
Controller -> Service -> Repository -> Database
```

1. Controller 只做请求边界工作，不开启数据库事务。
2. Service 是业务事务唯一所有者。
3. Repository 接收 Service 传入的 `*gorm.DB` 执行持久化，不决定业务事务范围。
4. 新代码统一使用 Service 包的 `RunInTransaction`。
5. 现有 `BasicRepository.ExecuteTx` 暂作为兼容入口保留，不批量迁移历史业务 Service。

本任务没有重构业务 Service、修改业务流程、改变 API、修改数据库结构，也没有开发 Organization、Integration、Data Permission、Report 或 Frontend。

## 5. 本次修复

### 5.1 Service 事务入口

新增 `RunInTransaction(ctx, db, fn)`：

1. 接收标准库 `context.Context`，兼容 HTTP 请求上下文和后台任务上下文。
2. 对 context、数据库连接和 callback 做稳定参数校验。
3. 使用 `db.WithContext(ctx).Transaction(fn)` 复用 GORM 原生提交、回滚和 savepoint 行为。
4. callback 返回的原始错误不转换、不吞掉，供上层按既有错误机制处理。
5. 传入已有事务时，明确创建嵌套 savepoint；内层错误是否继续回滚外层，由 Service 是否向外传播该错误决定。

### 5.2 Controller 架构守卫

新增自动测试扫描 Controller 生产代码：

1. 禁止导入 `gorm.io/gorm` 或内部数据库基础设施。
2. 禁止调用 `DBWithContext`、`ExecuteTx` 或 `RunInTransaction` 等事务入口。
3. 防止未来把事务入口从 Service 上移到 Controller。

### 5.3 未迁移历史业务 Service

历史 `ExecuteTx`、直接 GORM transaction 和业务方法保持原样。本任务只建立新代码基线，不通过机械替换扩大行为影响。

## 6. 推荐 Service 事务模板

```go
func (s *ExampleService) Change(ctx context.Context, req ChangeRequest) error {
	return RunInTransaction(ctx, s.db, func(tx *gorm.DB) error {
		if err := s.firstRepo.Update(tx, req.First); err != nil {
			return err
		}
		if err := s.secondRepo.Create(tx, req.Second); err != nil {
			return err
		}
		return nil
	})
}
```

必须遵守：

1. 在进入事务前完成无需锁定数据的参数校验和外部读取。
2. 事务内只执行需要原子一致性的数据库操作。
3. 所有 Repository 写操作必须使用 callback 收到的同一个 `tx`。
4. 不在事务内执行 HTTP、MQ、对象存储、SMTP、SMS 或其他不可回滚外部 I/O。
5. 缓存刷新、Casbin 等可重建外部状态在提交后执行，并按场景设计补偿。
6. 内部方法优先接收并复用现有 `tx`，不要无意开启嵌套事务。
7. 确需局部回滚时才显式嵌套 `RunInTransaction(ctx, tx, fn)`，并清楚处理 savepoint 错误。
8. callback 的任意错误必须直接返回，确保回滚和错误传播。
9. 关键状态迁移使用带旧状态条件的原子更新，并检查 `RowsAffected`。
10. 批量同步按单对象或小批次事务，不使用覆盖整个批次的长事务。

## 8. 测试内容

新增测试：

1. `TestRunInTransactionCommitsOnSuccess`
   - callback 成功时提交数据。

2. `TestRunInTransactionRollsBackAndPropagatesError`
   - callback 返回错误时回滚数据。
   - 原始错误可通过 `errors.Is` 继续识别。

3. `TestRunInTransactionNestedSavepoint`
   - 内层错误被外层处理时，只回滚内层 savepoint。
   - 外层事务可继续提交。

4. `TestRunInTransactionNestedErrorRollsBackOuterWhenPropagated`
   - 内层错误向外传播时，外层事务整体回滚。

5. `TestRunInTransactionValidatesRequiredInputs`
   - context、数据库和 callback 缺失时返回稳定错误。

6. `TestControllerLayerDoesNotOwnDatabaseTransactions`
   - 自动守卫 Controller 不持有 GORM 事务。

行为测试使用项目已有 `github.com/glebarez/sqlite` 真实执行 GORM transaction 和 savepoint，不以调用次数模拟事务结果。

## 10. 未修复问题

1. 历史 Service 仍混用三种事务调用方式。批量迁移可能改变 panic、context 和嵌套行为，应另设兼容性任务。
2. `BasicRepositoryImpl.ExecuteTx` 仍在 Repository 实现中创建事务；作为历史兼容入口保留，新代码应使用 Service 入口。
3. `FileRepositoryImpl.DeleteFile` 自行决定事务边界，不符合新基线；本任务不修改文件业务逻辑。
4. `SysUserService.ResetPassword` 的两次数据库更新可能部分成功。
5. `FileService.InitChunkUpload` 的分片记录循环创建可能留下部分数据。
6. 数据库授权与 Casbin、缓存、文件存储等外部状态无法依赖单一数据库事务保证一致，需要按具体模块设计补偿或可重建策略。
7. 历史状态更新缺少统一 compare-and-swap helper；P2A/P2B 新状态机不得复制该模式。
8. 任务开始前已有的 Report、Frontend、design 和其他历史改动继续保留，未纳入本任务。

## 11. 后续模块约束

Organization 与 Integration 后续开发必须遵守：

1. 单对象镜像落库、同步记录更新等一致性写入由 Service 开启事务。
2. 全量同步不得使用覆盖整个批次的大事务。
3. Integration HTTP 执行不得被数据库事务包裹。
4. Execution/Retry 抢占和 Sync Record 状态迁移必须使用原子条件更新。
5. Integration 与 Organization 不使用跨模块大事务；通过 Service 协议、BusinessLink 和可重试状态协调。
6. Controller、轻量 worker 和业务 handler 不直接管理 Repository 事务。
