## 2. 任务目标

本任务建立 Sweet Platform DTO Validation 最小兼容基线：

1. 保留 Gin `binding.Validator` 作为唯一 Validator engine。
2. 统一 Validator 初始化、字段名提取、中文/英文翻译和自定义 tag 注册。
3. 统一 Body、Query 和显式 DTO 校验的字段错误转换。
4. 固定 `required`、`min`、`max`、`oneof`、`gt`、`gte`、`lt`、`lte` 的使用基线。
5. 提供动态枚举、分页参数和已解析日期范围的通用校验 helper。
6. 保持 T005 已确定的参数错误响应结构和错误链。

本任务不批量修改历史 DTO，不修改业务接口、业务规则、前端、数据库、迁移、Seed、Report、Organization、Integration 或 Data Permission。

## 4. Validation 审计结果

### 4.1 Validator 初始化

| 检查项 | 审计结论 | 本任务处理 |
| --- | --- | --- |
| Validator engine | `initialize.InitValidators()` 使用 Gin `binding.Validator.Engine()`，是现有唯一初始化入口 | 保留入口，具体配置收敛到 `utils.InitializeValidator` |
| DTO tag | Gin engine 使用 `binding` tag | 在公共初始化中显式固定 |
| 字段名 | 原实现只读取 `json` tag | 统一为优先 `json`、其次 `form`、最后 Go 字段名 |
| 翻译 | 原实现注册中文、英文翻译，但忽略 translator 获取和注册错误 | 统一检查并返回初始化错误 |
| 自定义 tag | 已有 `non_empty_json` | 保留语义并移入公共初始化 |
| 自定义 JSON 校验 | 原实现对字段直接类型断言，错误类型使用 tag 时可能 panic | 改为安全类型判断和 JSON 解析 |

### 4.2 DTO tag 分布

审计 `backend/dto` 中现有 `binding` tag：

| Tag | 数量 | 结论 |
| --- | ---: | --- |
| `required` | 159 | 已广泛使用 |
| `required,min=1` | 2 | 少量 slice 最小长度校验 |
| `omitempty,non_empty_json` | 4 | Report JSON 配置使用 |
| `required,non_empty_json` | 2 | SMS JSON 配置使用 |
| `required,email` | 1 | 邮件配置使用 |

历史 DTO 尚未系统使用 `max`、`oneof`、`gt`、`gte`、`lt`、`lte`。本任务通过公共初始化和自动化测试固定这些内置规则，不批量改变历史接口行为。

### 4.3 错误转换

原 `ValidatorBody` 和 `ValidatorQuery` 各自实现一份 `validator.ValidationErrors` 翻译及拼接逻辑；另有一个无引用的 `TranslateError` 简化函数，存在第二套字段错误表达。

本任务：

1. 删除无引用的 `TranslateError`。
2. 使用 `ValidationIssues` 统一提取字段、规则、规则参数和消息。
3. 使用 `ValidationErrorMessage` 保持现有逗号拼接的客户端消息。
4. 使用 `ToValidationParameterError` 统一转换为 T005 的 parameter error。
5. 原始 binding/validator error 继续作为 `AdminError.Cause` 保留。

### 4.4 枚举

现有枚举以 string 或整数别名及常量为主，部分 string 枚举有独立 `Normalize*` 函数；DTO 多数只校验 `required`，没有统一枚举合法值校验。

新基线：

1. 静态、稳定枚举优先使用 `binding:"oneof=..."`。
2. 不能用静态 tag 表达的动态允许集合使用泛型 `ValidateEnum`。
3. `ValidateEnum` 返回标准 parameter error，不依赖错误字符串分支。
4. 本任务不修改现有 enum 文件和历史 DTO。

### 4.5 分页

`request.Basic` 的 `page` 和 `num` 当前没有 binding tag；Repository 查询层保留 `page=1`、`num=10` 默认值，并将页大小限制为最多 5000。部分历史业务还有自己的导出或报表页大小规则。

新基线：

1. `ValidatePagination(page, num)` 保留 `0` 表示“使用默认值”。
2. 显式负数 page/num 返回 parameter error。
3. 普通平台分页显式超过 5000 返回 parameter error。
4. 导出、Report 等特殊批量读取继续使用各自已评审的业务上限。
5. 本任务不自动将 helper 注入所有历史接口，避免改变现有默认和兼容行为。

### 4.6 日期范围

当前 Access Log 等业务在 Service 中自行解析字符串日期并判断开始、结束顺序，没有公共日期范围 helper。

新基线：

1. DTO 负责格式绑定或边界层负责字符串解析。
2. `ValidateDateRange(start, end)` 只校验已解析的 `time.Time`。
3. 任一边界为 zero value 时视为未提供，允许通过。
4. 完整范围中开始时间晚于结束时间时返回 parameter error。
5. 日期格式和时区属于具体 DTO/领域协议，本任务不强制全局格式。

## 6. Validation 使用规范

### 6.1 DTO tag

1. 必填：`required`
2. 字符串、集合长度：`min` / `max`
3. 静态枚举：`oneof`
4. 严格数值范围：`gt` / `lt`
5. 包含边界范围：`gte` / `lte`
6. 可选字段：先使用 `omitempty`，再追加实际规则
7. JSON 配置：按现有约定使用 `non_empty_json`

### 6.2 边界职责

1. Controller 继续通过 `ValidatorBody` / `ValidatorQuery` 绑定和校验。
2. 非 HTTP DTO 校验使用 `ValidateStruct`，不得创建私有 validator engine。
3. 动态枚举、分页和已解析日期范围使用公共 helper。
4. 依赖数据库或跨字段业务状态的复杂校验留在 Service。
5. Repository 不承担 DTO 校验和业务校验。

### 6.3 错误原则

1. 字段名使用客户端可见的 `json` 或 `form` 名称。
2. 校验失败统一为 HTTP 400、error code 20003。
3. 原始错误保留在错误链中，但不直接暴露给客户端。
4. 禁止通过错误消息字符串判断校验类型。
5. 不创建第二套 Validation response。

## 7. 测试覆盖

新增或扩展测试覆盖：

1. `required` 失败。
2. `min` / `max` 失败。
3. `oneof` 枚举失败。
4. `gt` / `gte` / `lt` / `lte` 数值边界失败。
5. 校验字段转换为 JSON 字段名。
6. `ValidateStruct` 输出标准 parameter error。
7. Body malformed JSON 输出标准 parameter error 并保留 cause。
8. Body DTO 字段错误输出翻译消息。
9. Query 类型错误输出标准 parameter error。
10. 静态 `oneof` 与动态 `ValidateEnum`。
11. 分页默认值、合法上限、负数和超限。
12. 正常、缺省和反向日期范围。
13. `non_empty_json` 非空对象通过、空数组失败。

## 11. 未处理问题

1. 历史 DTO 绝大多数只有 `required`，枚举和范围约束需由各业务 Task 按兼容性逐步补齐。
2. `request.Basic` 尚未自动调用 `ValidatePagination`；历史 Repository 仍保留默认和上限归一化。是否在新模块 Controller 模板中强制调用，应由后续 Controller Baseline Task 决定。
3. Access Log 等历史 Service 仍有本地日期解析和范围校验，本任务不做批量迁移。
4. 不同业务的日期格式、时区和最大查询窗口尚无统一协议，需在具体 API 详细设计中明确。
5. 枚举的静态 `oneof` 值仍需 DTO 作者与 enum 常量保持一致；本任务不引入枚举注册表或代码生成。
6. 历史 DTO 中存在“整数零值是否表示缺省还是非法”的语义差异，不能通过全局 tag 一次性修复。
