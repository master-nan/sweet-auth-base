## 2. Task 目标

本任务建立 Sweet Platform API Response 和 Error Handling 最小兼容基线：

1. 保持现有成功和失败 JSON 字段不变。
2. 明确 Controller 统一通过 `response.NewResponse()` 和 `ctx.Error(err)` 交给中间件输出。
3. 为业务错误增加参数、权限、业务、数据库、系统五类内部语义。
4. 支持稳定错误码、客户端消息、原始 cause 和标准错误链。
5. 未分类错误统一安全降级，不向客户端暴露底层数据库或系统错误。
6. Validator 的 JSON、Query 和字段校验错误统一转换为参数错误。

本任务不重构全部 Controller，不修改业务 API DTO，不修改前端接口，也不修改业务逻辑。

## 5. Response 规范

### 5.1 成功响应

后台 API 继续使用：

```json
{
  "success": true,
  "data": {},
  "message": "操作成功",
  "code": 200,
  "total": 0
}
```

规则：

1. Controller 创建 `response.NewResponse()` 并放入 Gin context 的 `response` key。
2. 单对象或命令结果使用 `SetData`。
3. 分页列表必须同时使用 `SetData` 和 `SetTotal`。
4. `ResponseHandler` 统一以 HTTP 200 输出成功响应。
5. 不创建第二套成功响应 DTO 或 Controller JSON helper。

### 5.2 错误响应

客户端结构保持：

```json
{
  "status_code": 400,
  "error_code": 20003,
  "error_message": "参数错误",
  "success": false
}
```

规则：

1. `Category` 和 `Cause` 使用 `json:"-"`，不改变客户端结构。
2. `StatusCode` 决定 HTTP 状态。
3. `ErrorCode` 是稳定平台/领域错误标识，不等于 HTTP 状态。
4. `ErrorMessage` 是允许向用户展示的安全消息。
5. `Success` 固定为 `false`。
6. `ForClient()` 创建无 cause 的独立输出对象，不修改共享 sentinel。

## 6. Error 规范

### 6.1 错误分类

| 分类 | 语义 | 默认对外行为 |
| --- | --- | --- |
| `parameter` | JSON、Query、Path、DTO 字段或枚举不合法 | HTTP 400，默认 code 20003 |
| `permission` | 未登录、认证失败、无功能权限 | HTTP 401/403，保留现有领域 code |
| `business` | 请求合法但违反业务规则 | 使用明确 HTTP 状态和领域 code |
| `database` | 数据库连接、约束或执行异常且未转成领域错误 | HTTP 500，code 10000，“系统异常” |
| `system` | 未分类异常、基础设施失败或程序错误 | HTTP 500，code 10000，“系统异常” |

### 6.2 错误码

1. 保留全部现有错误码和客户端字段，避免破坏 API 兼容。
2. `ErrorCodeParamInvalid = 20003` 是默认参数错误码。
3. `ErrorCodeGeneric = 10000` 是历史通用/系统兜底码；新增具体业务错误不得继续滥用该通用码。
4. 新模块错误码应在模块详细设计中分配稳定区间。
5. 错误码不能通过错误消息推断，也不能使用 `err.Error()` 字符串比较。

### 6.3 构造与包装

新增基础入口：

- `NewClassifiedError`
- `WrapError`
- `NewParameterError`
- `WrapParameterError`
- `NewPermissionError`
- `NewBusinessError`
- `WrapBusinessError`
- `WrapDatabaseError`
- `WrapSystemError`
- `CategoryOf`
- `ToClientError`

规则：

1. Service 返回已有领域错误时可直接返回。
2. 增加上下文时使用 `%w` 或上述 `Wrap*` 方法，不使用 `errors.New(err.Error())`。
3. Repository 的原始数据库错误由 Service 判断：可识别场景转换为业务错误，其他场景使用 `WrapDatabaseError`。
4. Controller 不解释 Service 错误，只执行 `_ = ctx.Error(err)` 并立即返回。
5. 中间件使用 `errors.As` 解析整个错误链。
6. 未知错误不会把原始 message 返回客户端。

## 7. Validator 规范

`ValidatorBody` 和 `ValidatorQuery` 现在统一：

1. 空 body、JSON 语法错误、JSON 类型错误、Query 类型错误均返回 parameter error。
2. DTO validation error 保留现有中文翻译消息。
3. 原始 binding/validation error 作为 `Cause` 保留，可通过 `errors.Is/As` 追踪。
4. 客户端只看到安全参数消息，不看到 JSON parser 或 Go 类型细节。

## 8. Controller 统一输出

推荐模式保持现状：

```go
func (c *ExampleController) Handle(ctx *gin.Context) {
	resp := response.NewResponse()
	ctx.Set("response", resp)

	var req request.ExampleReq
	if err := utils.ValidatorBody(ctx, &req, c.translator); err != nil {
		_ = ctx.Error(err)
		return
	}
	result, err := c.service.Execute(ctx, req)
	if err != nil {
		_ = ctx.Error(err)
		return
	}
	resp.SetData(result)
}
```

Controller 禁止：

1. 根据错误字符串决定响应。
2. 把数据库错误包装为 `NewBadRequestError(err.Error())`。
3. 直接构造另一套 JSON 错误。
4. 在调用 `ctx.Error` 后继续执行业务逻辑。

## 12. 未处理问题

1. 15 处历史 Controller 仍使用 `NewBadRequestError(err.Error())`；批量修改可能改变客户端 message 和状态码，应单独审计。
2. `backend/api/auth_api.go` 和 `backend/middleware/auth.go` 还有 3 处相同原始消息重包装。
3. `NoRouteHandler` 的 404 JSON 不符合 `AdminError`；统一时需要评估前端和外部调用方兼容性。
4. `CustomRecovery` 和部分 Auth 中间件仍直接使用历史全局错误对象，当前 JSON 兼容但后续可统一走 `ToClientError`。
5. 现有错误码没有集中注册表，且历史通用 code 10000 同时用于 400 和 500；本任务只定义新代码使用规则，不重编号。
6. 部分历史错误 HTTP 状态语义不准确，例如“应用名称已存在”仍使用 401；为保持 API 兼容，本任务只修正内部 category，不修改状态码。
7. 数据库错误只有在 Service 显式调用 `WrapDatabaseError` 时才标识为 database；未包装的未知底层错误按 system 安全处理。
8. 任务开始前已有的 Report、Frontend、design 和其他历史改动继续保留，未纳入本任务。
