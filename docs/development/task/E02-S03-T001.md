本 Task 在既有 Organization Service 边界内增加以下只读能力：

1. 企业人员分页、详情和 options。
2. 人员绑定账号状态和安全账号摘要。

## 4. 实际模型与字段审计

### 4.1 `org_employee`

1. 内部人员标识为 `id`，业务查询和 options 返回 `employee_id` 语义的内部 ID。
2. 源唯一约束包括 `source_system_code + source_id`、`source_system_code + employee_no` 和非空 `source_code` 组合。
3. `user_id` 类型为可空 `*int`，通过 `WHERE user_id IS NOT NULL` 的 partial unique index 保证一个账号最多绑定一个员工。
4. `user_id` 是平台扩展字段，不是人员源主数据。
5. 人员有效性字段是 `employment_status`、`source_deleted`、`valid_from` 和 `valid_to`；模型没有通用 `status` 字段。
6. 当前有效就业状态采用已评审字典中的 `active`、`probation`；`suspended`、`resigned`、`retired` 默认不可新选。

### 4.2 `org_position`

1. 岗位内部标识为 `id`，options 只返回 `position_id` 语义的内部 ID。
2. 岗位直接通过 `org_unit_id` 归属管理组织，不在人员表冗余唯一岗位。
3. 法人筛选通过岗位所属 `org_unit.primary_legal_entity_id`，不把任职所在法人误认为岗位归属。
4. 唯一约束包括源标识、源编码、平台编码，以及当前有效岗位的组织内编码约束。
5. 有效性使用 `status`、`source_deleted`、`valid_from` 和 `valid_to`。

### 4.3 `org_assignment`

1. 任职真实关联字段为 `employee_id`、`legal_entity_id`、`org_unit_id` 和可空 `position_id`。
2. 人员按法人、组织、岗位筛选只读取任职关系，不新增任职 API。
3. 本 Task 不读取、推断或返回主任职，不自动选取第一条任职。

### 4.4 `sys_user`

1. 平台账号字段包含 `user_name`、密码、邮箱、手机号、Token、登录时间、角色等。
2. 当前模型没有可安全复用的独立账号状态字段，因此普通人员响应不臆造 `account_status`。
3. 账号摘要仅批量投影 `id` 和 `user_name`；不返回密码、Token、角色、登录安全字段、账号联系方式。

### 4.5 元数据差异

`org_employee` 模型存在手机号和邮箱，但 T002 已提交元数据明确不将二者开放为列表、快速查询或高级查询字段。为遵守既有隐私和元数据边界，本 Task 的人员 QuickQuery 只使用 `employee_no` 和 `name`，不绕过元数据搜索手机号或邮箱；详情只返回脱敏联系方式。

## 5. 领域与 DTO 边界

1. `employee_id`、`position_id`、`org_unit_id`、`legal_entity_id`、`user_id` 各自保持独立语义。
2. 人员和岗位 Request DTO 支持分页、QuickQuery、AdvancedQuery、有效性、历史回显和受控关联筛选。
3. Response 全部使用白名单 DTO，不直接返回 Model。
4. 人员列表返回绑定状态；已绑定时可返回 `user_id + user_name` 安全摘要。
5. 人员详情只返回 `mobile_masked`、`email_masked`，不返回原始联系方式。
6. 岗位详情可返回所属组织和法人安全摘要，不返回人员清单。
7. 普通响应不返回 `source_id`、`source_version`、`sync_status` 或同步错误详情。

## 6. 人员查询能力

1. `QueryEmployees` 支持分页、QuickQuery、AdvancedQuery、人员状态、绑定状态、法人、组织、岗位和时间范围。
2. `bound_status` 支持 `all`、`bound`、`unbound`。
3. `GetEmployeeDetail` 只按内部 `employee_id` 查询，并应用相同有效性边界。
4. `QueryEmployeeOptions` 的 value 固定为 `employee_id`，label 为“工号 - 姓名”。
5. options 默认只返回当前有效人员；停用和历史值仅通过最多 100 个 `selected_ids` 回显，并标记为 disabled。

## 7. 岗位查询能力

1. `QueryPositions` 支持分页、QuickQuery、AdvancedQuery、法人、组织、岗位类型、管理岗位、状态和时间范围。
2. `GetPositionDetail` 只按内部 `position_id` 查询。
3. `QueryPositionOptions` 的 value 固定为 `position_id`，label 为“岗位编码 - 岗位名称”。
4. options 默认只返回当前有效岗位；停用和历史值仅通过受限 `selected_ids` 回显。

## 8. 多任职分页和联合筛选

人员关系筛选使用一个参数化关联子查询：

```text
EXISTS (
  org_assignment
  WHERE employee_id = org_employee.id
    AND legal_entity_id = ?
    AND org_unit_id = ?
    AND position_id = ?
    AND 任职有效性条件
)
```

所有已传入的法人、组织和岗位条件都作用于同一条任职。`EXISTS` 不扩张人员结果集，因此：

1. 多条任职不会产生重复人员。
2. total 是去重后的人员总数。
3. 不使用应用层全量去重或内存分页。
4. 不使用 PostgreSQL 专属 `DISTINCT ON`。

## 9. 有效性与历史回显

1. `only_effective` 默认 true。
2. 人员当前有效要求就业状态为 `active/probation`、未源删除且指定日期落在有效期内。
3. 岗位当前有效要求状态为 `enabled`、未源删除且指定日期落在有效期内。
4. `include_disabled` 显式开放停用状态，但仍遵守源删除和有效期。
5. `include_history` 显式开放源删除和历史有效期，但不自动开放停用状态。
6. `only_effective=false` 同时开放停用和历史范围。
7. `valid_from`、`valid_to` 当日均为包含边界。

## 11. 性能和查询次数

1. 人员分页使用数据库 count + 分页 rows，不在应用层全量分页。
2. 多任职关系通过 `EXISTS` 过滤，不产生重复行。
3. 人员账号摘要对当前页所有 `user_id` 去重后执行一次批量查询。
4. 带账号摘要的人员列表固定为 count、rows、账号批量读取三次查询，不随行数增长。
5. 人员 options 不读取账号摘要。
6. 岗位列表不逐行读取组织或法人；岗位详情仅按需读取单个组织和法人摘要。
7. selected IDs 最多 100，普通 options 复用平台分页上限。
8. 本 Task 没有增加缓存或索引；现有任职单列索引支持 V1 条件，组合查询索引优化留待真实数据量和 PostgreSQL 执行计划评估。
